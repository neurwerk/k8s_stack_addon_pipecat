# Development and publication

Use `mise install`, `uv sync --frozen`, and `npm ci --prefix frontend`. `mise exec -- make check BASE=/absolute/path/to/reviewed-base` runs tooling checks, add-on composition, linting, resource schemas, Compose configuration, Python/TypeScript static checks, reviewed security tests, and package/frontend builds. `BASE` explicitly selects the Base checkout for composition and cross-chart tests. Product tooling installs the exact shared release wheel from its reviewed lock; no sibling Tooling checkout is required. Checking a working candidate does not establish immutable release compatibility. Automated frontend tests are intentionally absent; manually verify login, microphone permission, bounded WebRTC/fresh WebSocket fallback, start/end/mute, error states, audio and notices when browser/media testing is authorized. WebSocket's upstream browser transport is intended for development/testing; it is not a promise of production-equivalent WebRTC behavior.

`make image-build` builds the local shared image. `compose.yaml` mounts an ignored local JSON configuration and credentials; put it behind a local HTTPS reverse proxy at the configured `public_origin`. Secure cookies deliberately do not have an insecure development fallback. A health probe/import or model-loading check must not trigger STT, TTS or model requests. The image contains Pipecat's packaged Silero and SmartTurn ONNX models and the compiled browser UI; no runtime model downloads are expected.

The check workflow builds without pushing and verifies bundled model loading with networking disabled. Image publication is a separate manual workflow with an `image-publication` environment approval, an approved full commit on main and a matching exact package version. Configure that protected environment before use. Do not run publication as part of ordinary PR checks. Publication itself does not authorize a chart pin, release tag, client adoption or reconciliation; verify registry digest, architecture and OCI revision/version/source labels independently, then submit the exact image pin and release-status change for review. Never overwrite an existing published version.

After first runtime publication, a package administrator changes the GHCR package visibility to Public. The `Publish approved runtime` workflow's ordinary `verify-public` job pulls anonymously on a fresh runner with an empty Docker configuration and verifies the version/digest, architecture and OCI labels. If verification fails before visibility is changed, make the manual change, then select **Re-run failed jobs** on that run to retry `verify-public` without rerunning the successful `publish` job. Inspect other verification failures before retrying. Do not select **Re-run all jobs**, rebuild an existing version, or overwrite its tag. No additional environment or reviewer configuration is needed. The `Build and Push Add-on Tooling` workflow uses the same anonymous verification sequence before artifact notes are published.

The manifest defines availability and prerequisite versions. Runtime publication, installation-specific credentials, explicit OIDC approval and gateway client authorization are deployment prerequisites. Voice requires an accepted model/binding and compatible speech endpoints. Optional TURN routing is checked separately and does not gate UI-only deployment. No live service calls or cluster access are part of the offline checks.

Pipecat-specific validation and app publishing live in the independent [tooling package and image](tooling/README.md); use the [sample app and CLI](scripts.md) for offline source validation. Shared Tooling parses the manifest; shared `stack-setup` owns custody, credential preparation and scoped access. Charts and client Flux definitions own deployment reconciliation, not SDK/setup lifecycle orchestration. Product code never receives root authority. Passing source checks does not establish publication or live browser/media acceptance; staged artifacts remain unavailable until independently verified.
