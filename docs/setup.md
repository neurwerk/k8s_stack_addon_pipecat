# Configuration and setup

## Release and configuration

The client owns immutable `pipecat-addon` source selection and Flux ordering: `namespaces` → `secret-sync` → `setup` → `app`, using paths from `release/manifest.yaml`. Stage secret delivery without waiting for credentials before preparation by shared `stack-setup`. Charts and Flux own browser OIDC, machine Jobs, bridge grant descriptors and certificate approvals; the SDK and product validator do not orchestrate their lifecycle. No database, Redis or session-signing Secret is needed.

Set `pipecat.enabled` and `pipecat.hostname` in client values. Supply `client-values` and `pipecat-product-values` in `pipecat`, `auth-keycloak`, `auth-keycloak-api-key-bridge` and `infra-cert-manager`; certificate approval consumes both inputs. Set the full published runtime image version with its independently verified digest. There is no default image; never deploy `validation/values.yaml`.

Each bot has a kebab-case Kubernetes `id` and independent `urlSlug` accepting underscores: `id: simple-chatbot`, `urlSlug: simple_chatbot` serves `/simple_chatbot/`. IDs `turn` and `product-values` are reserved for shared resources. Set `anonymous` explicitly. `enabled` defaults to true; false removes only that bot's workload, retaining identity and credential setup ownership. `sessionsEnabled` defaults to false: UI, login and health can deploy without speech endpoints, but voice admission is denied. Credential preparation is independent of voice availability. See [app publishing](scripts.md) for the source format and CLI.

Enabled sessions require canonical `modelId`, gateway routing and `stt`/`tts` settings. A bot's `gatewayBaseUrl` selects an approved gateway API base URL; otherwise `pipecat.gatewayOrigin` and `bindingId` select `/bindings/<bindingId>/v1`. Never use a direct provider URL. Speech settings contain `baseUrl`, `model`, optional `secretRef: {name, key}`, TTS `voice` and STT `language`. STT uploads bounded VAD-segmented WAV to `/audio/transcriptions` with JSON output. TTS requests `/audio/speech` with `response_format=pcm`: signed little-endian PCM16, 24 kHz mono, not WAV. Accepted media types are `audio/pcm`, `audio/x-pcm` and `application/octet-stream`; known container/error prefixes are rejected before audio emission. Speech services use separate credentials; raw microphone audio is not processed by the model gateway's PII protection.

`sessionSeconds`, `idleSeconds` and `maxConnections` bound call duration, inactivity and concurrency. There is one active call per browser session. Restarts discard calls/history; protected sessions end no later than token expiry and do not refresh automatically. Use a short maintenance window rather than staged rollouts.

## Credentials and namespace isolation

`release/manifest.yaml` is the single setup definition. Client `config/addons.yaml` references namespaced Flux sources and selects features, bot instances and exact readers. Setup generates credentials; charts deliver approved fields directly into application Secrets. Browser, machine and gateway credentials use 32 random bytes in unpadded base64url; TURN uses 32 random bytes in lowercase hex. Speech keys are supplied, never randomly generated. There is no human-password handover.

| OpenBao record | Property | Kubernetes target |
| --- | --- | --- |
| `addons/pipecat/oidc` | `clientSecret` | `pipecat-oidc-secret/clientSecret` in `auth-keycloak` and `pipecat` |
| `addons/pipecat/turn` | `sharedSecret` | `pipecat/pipecat-turn-secret/sharedSecret` |
| `addons/pipecat/bots/<id>` | `gatewayApiKey`, selected `sttApiKey`/`ttsApiKey` | `pipecat/pipecat-bot-<id>` |
| `addons/pipecat/machines/<id>` | `clientSecret` | `auth-keycloak/pipecat-bot-<id>-oidc/clientSecret` |
| `addons/pipecat/verifiers/<id>` | `gatewayApiKeySha256` only | `auth-keycloak-api-key-bridge/pipecat-bot-<id>-verifier/apiKeySha256` |

Enable `pipecat.secretSync.enabled` for managed delivery through the standard namespace-local `<namespace>-openbao-secret-store` names. Clean enrollment uses role `addon-pipecat-runtime` with `pipecat-external-secrets` and the existing `pipecat-openbao-secret-store` name. Base reader roles `auth-keycloak` and `auth-keycloak-api-key-bridge` keep their exact existing ServiceAccount/SecretStore bindings. Runtime reads selected `oidc`, `turn` and bot records; Keycloak reads selected `oidc` and machine records; bridge reads **only selected verifier records**, never raw keys. These are exact record grants, not wildcard grants. `pipecat-identity-secrets` owns auth delivery; `pipecat-verifier-secrets` stages verifier delivery before machine provisioning. `pipecat-gateway-registrations` publishes grant descriptors after machines. Generic `secretDeliveries` are confined to runtime/external records, not Pipecat-owned paths, and require separately declared client ownership. Do not give two resources ownership of the same Secret.

With managed sync disabled, `pipecat.oidc.secretName` and `secretKey` select the namespace-local reference used by both runtime and browser provisioning. The operator supplies matching existing credentials in `pipecat` and `auth-keycloak`; charts do not copy credentials between namespaces.

Managed bot preparation selects `secretSync.enabled`, `anonymous: true`, nonempty `gatewayPermissions`, and a default or exact canonical gateway SecretRef. Include the canonical `modelId` and its invocation permission even with voice disabled. Existing external gateway/speech refs are not imported, generated or overwritten and do not select managed machine/verifier records. Reserved `pipecat-bot-` refs must match their bot and field exactly. Speech keys are selected only through exact refs to `pipecat-bot-<id>/sttApiKey` or `ttsApiKey`. Disabling managed sync does not disable active OIDC/TURN consumers using existing Secrets. Retain credentials/data on removal; deletion requires separate approval.

## Browser and machine identities

Keycloak/OIDC configuration, including `pipecat.oidc.issuer`, is required for every app, including anonymous and disabled entries. A nonempty bot catalog cannot disable OIDC. `anonymous: true` is an explicit client access policy, not a way to omit identity setup: anonymous bots use their scoped bot key even after login; protected bots use only the signed-in user's delegated token. No denied user request is retried with a bot credential.

The browser client is `pipecat`; callbacks are exact `https://<hostname>/<urlSlug>/auth/callback` URLs, with matching HTTPS origin. Supply trusted `pipecat-oidc-approval-values` in `auth-keycloak` with explicit Base `clientApproval` for client ID, `pipecat-user` role, `agentgateway` audience and requested gateway permissions. Set `pipecat.oidc.gatewayPermissions` to the same reviewed scope. Approval scopes existing user permissions, not new grants. Base must approve the browser client and selected bindings as gateway callers. Use `/access/neurwerk-pipecat-users` for login admission. Cookies are secure, HttpOnly and path-scoped; state, nonce, PKCE and signed issuer/audience/expiry/authorized-client checks protect login. Tokens stay on the server.

`keycloak-pipecat-machines` invokes packaged `upsert-scoped-service-client` for selected managed bots. It receives `KC_CLIENT_ID`, Secret-backed `KC_CLIENT_SECRET`, `KC_REALM_ROLE_SCOPE=[]`, `KC_GATEWAY_ROLE_SCOPE`, `KC_CLIENT_AUDIENCES=["agentgateway"]` and `KC_CLIENT_APPROVAL`, plus existing Keycloak administrative connection settings. Supply each `pipecat.machineIdentityApprovals.<id>` through trusted client configuration as exactly `{clientId, realmRoles: [], gatewayPermissions, audiences: [agentgateway]}`. The Job passes this object directly, never generating an approval from requested roles. The requested model/provider roles must match approval and the approved gateway role catalog.

Machines are distinct `pipecat-bot-<id>` clients: service accounts on, browser/password flows and full scope off, exact role assignments/scopes with stale roles revoked and readback verification. The helper refuses unowned existing identities and unrelated clients. The descriptor HelmRelease waits for machine provisioning, then produces version-2 `service_account` grants in `pipecat-bot-<id>-grant/grant.json`. The client registers each grant/verifier pair through Base's `authKeycloakApiKeyBridge.managedRegistrations`. A descriptor alone does not create an account.

`upsert-scoped-service-client` handles machine reconciliation. `pipecat.machineIdentity.image` pins that shared helper independently of the product tooling image. Service requests and trusted client approvals remain explicit chart inputs; neither product settings nor the offline validator mint their own approvals. Existing SecretRefs and protected UI-only bots without managed selections remain supported. Candidate source validation is not publication evidence.

## Media and deployment readiness

UI, signaling and WebSocket fallback use ordinary Traefik HTTPS 443. The browser tries WebRTC first with a 15-second networking timeout after microphone permission. Only an initial connection failure permits clean cancellation and one fresh, session-ticket-bound WebSocket attempt. Permission, auth and model/service errors do not trigger fallback; there is no seamless mid-call switching. End retires an attempt's callbacks and clients; a new Start waits for acknowledged cleanup. Failed cleanup requires reloading rather than overlapping calls.

The WebRTC data channel permits one bounded client-ready handshake and required bounded ping/track-status messages before upstream queuing/RTVI. Raw-audio batches, files, injected text and function-call results are unsupported. WebSocket uses Pipecat's browser development/testing transport, bounded PCM16 microphone frames at 16 kHz mono and 24 kHz playback; browser support, echo handling and latency require manual verification. It needs working HTTPS/WebSocket routing, not functioning TURN.

Optional coturn is chart-managed with `pipecat.turn.enabled`, configurable `hostname`, and `pipecat-turn-secret/sharedSecret` containing 64 lowercase hex characters. Managed TURN is browser-only: expiring HMAC REST credentials reach browsers; the shared secret stays server-side and server ICE settings remain separate. Its cert-manager TLS certificate uses the configured exact hostname and approved issuer; DNS01 does not need HTTP challenge forwarding. No public STUN service is a default.

Browsers connect to `turns:<hostname>:443?transport=tcp`; the existing edge HAProxy routes that hostname by SNI to the selected cluster node's TCP NodePort 30549 → coturn TLS 5349. Relays use the TURN Pod's private IPv4 address and internal UDP ports 31000–31015 toward bot Pods. Do not expose UDP listeners/relay ports publicly or configure `external-ip`. The chart performs no edge/EC2 changes. Pin the TURN Pod with `turn.nodeSelector`; `externalTrafficPolicy: Local` requires forwarding to that node. Set explicit `turn.peerAddressRanges` to the client's bot Pod IPv4 ranges in start-end form, for example `["10.42.0.1-10.42.0.254"]`, and use a client-selected node label such as `{kubernetes.io/hostname: example-turn-node}`. These synthetic values are not deployment defaults. Permit the private relay path in cluster networking and egress rules. Include `pipecat` in both Reloader's watch and RBAC namespace lists so TLS renewal and shared-secret rotation reload coturn through a Pod replacement.

The shared release does not wait for optional TURN certificate/startup, so public routing work cannot block HTTPS fallback. Check TURN separately. Fill `pipecat.egress` with narrow identity/JWKS, gateway, speech, optional S3 and TURN peers/ports; only DNS is allowed by default. For optional Rook/External Secrets, add genuine client Flux dependencies and generated Secret/user/bucket health checks before consumers. Complete client selection and credential reconciliation are required. Public TLS, browser media and inference readiness are separate operator acceptance checks, never inferred from pod health. Keep PII notices enabled: they appear in the UI, not speech or ordinary assistant history; reasoning/tool control data is not spoken.
